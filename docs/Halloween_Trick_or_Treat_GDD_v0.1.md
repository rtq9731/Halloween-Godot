# TRICK OR TREAT! — 할로윈 단편 게임 기획서

> **문서 버전:** v0.1 · 2026-10-12  
> **개발 대상:** Godot 4 + GDScript / 세로형 웹게임 / PC·모바일 브라우저  
> **형식:** 할로윈 합작용 미니게임, 단일 플레이, 기록 경쟁  
> **상태:** 콘셉트·핵심 조작 확정 / 수치·콘텐츠 규모는 프로토타입에서 검증

---

## 0. 한눈에 보기

**한 줄 소개:** 할로윈 밤, 눈치 빠른 꼬맹이가 되어 마주치는 주민의 모습과 말투를 읽고 **TRICK 또는 TREAT**을 골라 제한시간 안에 사탕을 최대한 많이 모은다.

**플레이어 경험:**
- 주민이 나타나면 약 **10초 안에** 외형, 현재 상태, 대사에서 힌트를 읽는다.
- 카드를 **왼쪽(TRICK) / 오른쪽(TREAT)** 으로 밀어 선택한다.
- 선택에 따라 획득 사탕 수가 달라지고, 곧바로 다음 주민으로 넘어간다.
- 같은 주민도 다시 만날 때 **상태·대사·반응이 달라질 수 있다**.
- 전체 제한시간이 끝나면 총 사탕 수와 최고 기록을 확인하고 즉시 재도전한다.

**디자인 원칙:** 외워서 찍는 게임이 아니라 **관찰 → 추론 → 빠른 선택**으로 점수가 올라가는 게임. 할로윈 특유의 장난기 있고 귀여운 분위기를 우선하며, 공포 연출은 필수가 아니다.

## 1. 게임 플레이 루프

1. **등장:** 다음 집의 주민 카드가 나타나며 개인별 **10초 선택 타이머**가 시작된다.
2. **관찰:** 주민의 인상, 소지품, 표정, 의상, 짧은 대사·상태 묘사를 확인한다.
3. **선택:** 카드를 왼쪽으로 밀면 `TRICK`, 오른쪽으로 밀면 `TREAT`.
4. **판정:** 고정 성향 + 이번 방문의 상태를 적용해 사탕 보상을 결정한다.
5. **피드백:** 반응 대사, 사탕 변화량, 짧은 애니메이션을 보인다.
6. **다음 사람:** 카드가 교체되고 타이머가 다시 시작된다. 전체 게임 시간은 계속 흐른다.
7. **종료:** 전체 게임 시간이 0이 되면 최종 사탕·최고 기록을 보여준다.

### 1.1 시간 체계

- `run_time_limit = 180.0`: 한 판 전체의 남은 시간. 초기값 3분, 데이터로 조절 가능.
- `decision_time_limit = 10.0`: 주민 카드 하나당 선택 가능한 최대 시간. **이 값은 핵심 규칙.**
- **전체 타이머는 플레이 중 항상 흐른다.** 카드 대기·고민 시간이 실질적인 기회비용이다.
- **선택 타이머는 카드 활성화 시 시작하고 선택 확정·시간초과 시 종료**한다.
- 시간 초과 처리 기본안: 보상 없이 카드 퇴장, 다음 카드. 별도의 장기 페널티는 MVP에서 생략.
- 반응 연출 목표: 약 `0.35~0.6초`. 이 연출도 전체 시간에 포함할지 테스트할 것. **MVP 권장: 포함하되 일정하게 짧게 유지.**
- 남은 전체 시간이 10초 미만이면 카드의 실제 선택 가능 시간은 남은 전체 시간까지만 허용한다.

### 1.2 사탕 점수

- 사탕 수는 한 판 동안 누적되는 **유일한 핵심 점수**.
- 각 선택은 주민의 상태·성향에 따라 `0 / 소량 / 대량` 등 서로 다른 보상을 준다.
- **TRICK이 무조건 고위험 고보상인 것은 아니다.** 사람에 따라 `TREAT`이 최고 보상일 수도 있고, 심술궂은 사람은 장난을 좋아할 수도 있다.
- 잘못된 선택도 결과 대사를 통해 이유를 추론 가능해야 한다.
- 보상은 우선 정수(`candy_delta`)로 처리한다. 사탕 회수·몰수 등 음수 점수는 **추가 실험용**으로 두고 MVP에서는 기본적으로 0 이상을 권장한다.
- 최고기록은 브라우저에서 로컬 저장한다. 로그인, 서버 순위표는 MVP 범위 밖이다.

### 1.3 숙련도 설계 원칙

**운이 아니라 눈치가 실력이어야 한다.**

- 같은 외형만 보고 선택할 수 없도록 **현재 상태가 의미 있게 판정을 수정**한다.
- 그렇다고 결과를 임의로 뒤집지 않는다. 모든 상태에는 **가독성 있는 단서**가 있다.
- 주민의 기본 성향을 학습하면 빠르게 추론할 수 있지만, 상태를 무시하면 오답이 나올 수 있다.
- 장난스러운 예외는 허용하되, 선택 후에는 플레이어가 '그래서 그랬구나'라고 납득할 수 있어야 한다.
- 캐릭터별 대사는 **10초 안에 읽히는 길이**로 제한한다.

## 2. 화면·레이아웃 명세

### 2.1 화면 방향 / 기술 기준

- 디자인 기준 해상도: **720 × 1280**, 세로(9:16 근사).
- 스마트폰에서는 가능한 가용 화면에 맞춰 레이아웃 스케일링; **노치, 상태바, 하단 홈 인디케이터 영역(safe area) 고려**.
- PC 브라우저에서는 중앙에 세로 게임 영역 배치, 주변 여백은 할로윈 밤 배경으로 채운다.
- 아주 작은 세로 화면에서도 **대사와 카드·타이머가 동시에 보이는 것**을 우선한다.
- Godot `Control` / `Container` / 앵커 중심 UI. 특정 픽셀 위치로 모든 요소를 고정하지 않는다.
- 웹 브라우저용 Godot 4 프로젝트는 **GDScript + Compatibility 렌더러**를 사용한다.

### 2.2 화면 구성(우선순위 순)

| 영역 | 권장 비중 | 표시 정보 | 원칙 |
|---|---:|---|---|
| 최상단 HUD | 약 10% | 전체 남은 시간, 누적 사탕 | 한눈에 읽혀야 함 |
| 선택 타이머 | 약 4% | 주민별 10초 바, 잔여 초 | 압박감은 주되 시선 방해 최소화 |
| 인물 대사 | 약 13% | 1~2줄 대사, 상태 단서 | 화면 스와이프 중에도 읽을 수 있게 |
| 카드/초상 | 약 55~60% | 주민 초상, 표정, 소지품, 이름 | **메인 시각 요소**, 단서 가독성 최우선 |
| 하단 안내·결과 | 잔여 | 좌우 방향 가이드, 선택 직후 반응 | 입력 방해 금지 |

> 비중은 고정 규격이 아니라 조정용 출발점. 화면 비율이 바뀌면 **주민 카드 높이를 탄력적으로 조절**하고 작은 화면에서 텍스트/버튼이 잘리지 않도록 한다.

### 2.4 스와이프 세부 동작 — Reigns 참고

1. **대기:** 카드가 화면 중앙에 배치된다. 양쪽 선택은 간결하게 안내한다.
2. **드래그:** 마우스/손가락 위치의 X 이동량에 따라 카드가 좌우로 이동하고 **최대 약 12°** 기울어진다.
3. **방향 표시:** 왼쪽으로 밀면 `TRICK`, 오른쪽으로 밀면 `TREAT` 문구가 강하게 나타난다.
4. **취소:** 임계치 미만에서 손을 떼면 카드가 부드럽게 중앙으로 복귀한다. **이때 선택 시간은 초기화되지 않는다.**
5. **확정:** 임계치 이상에서 떼면 카드가 화면 밖으로 퇴장하고 선택 결과를 적용한다.
6. **교체:** 다음 카드가 간단한 전환 애니메이션으로 등장한다.
7. **보조 입력:** PC의 `← / →` 방향키도 같은 선택을 실행하도록 한다. 스와이프가 어려운 환경을 위한 클릭형 좌/우 보조 조작은 옵션으로 둔다.

**터치 주의:** 카드 드래그 도중 브라우저의 페이지 스크롤·뒤로가기 제스처와 충돌하지 않도록 입력 영역과 웹 페이지 오버플로우를 설계·테스트한다. 선택 확정 직전의 좌/우 판정을 분명히 하고, 작은 이동으로 오입력되지 않도록 한다.

## 3. 인물/상태/대사 시스템

### 3.1 세 계층으로 분리

**A. CharacterDefinition — 고정 인물**
- `id`, 표시 이름, 기본 캐릭터 아트, 기본 성향, 변하지 않는 특성.
- 예: `vampire_parent` / '뱀파이어 아저씨' / 조용함을 선호하나 상황에 따라 장난도 즐김.

**B. EncounterVariant — 등장 시 변하는 상태**
- 현재 기분·상황, 포즈/표정/소지품, 상태 단서, 대응 규칙.
- 예: '아기를 겨우 재움' / '할로윈 장난 준비 중'.

**C. DialogueVariant — 자연스러운 대사 변형**
- 같은 상태에서 여러 짧은 대사를 돌려 사용하되, **선택 판단에 필요한 정보가 유지**되어야 함.
- 대사가 단서와 충돌하면 안 된다. 랜덤 대사는 사실상 동일한 상황을 다르게 표현하는 용도로 사용.

**중요:** `(character, state)` 조합마다 `TRICK`, `TREAT`의 보상과 결과 반응을 데이터로 정한다. **선택 순간 임의로 정답을 뒤집지 않는다.**

### 3.2 예시 인카운터(확정 콘텐츠 아님)

| 인물 | 이번 상태·단서 | TRICK | TREAT | 판단 근거 |
|---|---|---:|---:|---|
| 뱀파이어 아저씨 | 아기 겨우 재움, 조용히 해 달라고 함 | +0 | +6 | 소음·장난을 싫어함 |
| 뱀파이어 아저씨 | 할로윈 장난 상대 기다림, 장난감 소지 | +10 | +3 | 장난에 참여하면 더 신남 |
| 마녀 | 마법 실패로 피곤함, 한숨 쉬는 중 | +1 | +7 | 지금은 얌전한 방문을 선호 |
| 마녀 | 장난 마법을 시험하려 함, 들뜬 표정 | +12 | +2 | 장난 경쟁을 반김 |
| 무뚝뚝한 할아버지 | 귀가 잘 안 들림, 손짓을 기다림 | +0 | +5 | 큰 소리보다 명확한 사탕 요청에 반응 |
| 무뚝뚝한 할아버지 | 장난감 거미로 아이 놀릴 준비 | +8 | +3 | 장난을 걸어주길 기다림 |

이 표의 보상은 **테스트용 가상 수치**다. 실제 구현에서 분포·평균 수익을 플레이테스트로 조정한다.

### 3.3 데이터 구조 예시(JSON 형식 설명용)

```json
{
  "character_id": "vampire_parent",
  "display_name": "뱀파이어 아저씨",
  "portrait": "res://assets/characters/vampire/base.png",
  "variants": [
    {
      "state_id": "sleeping_baby",
      "weight": 1.0,
      "state_hint": "눈 밑이 퀭하다. 집 안에서 아기 울음소리가 들린다.",
      "dialogues": [
        "쉿! 애 겨우 재웠단 말이야.",
        "제발 조용히 좀 해줄래?"
      ],
      "expression": "tired",
      "trick": { "candy_delta": 0, "reaction": "애가 깼잖아!" },
      "treat": { "candy_delta": 6, "reaction": "여기 사탕. 이제 조용히 가렴." }
    }
  ]
}
```

권장 실제 Godot 저장 방법: `Resource` 기반 `CharacterData` / `EncounterData`를 기본으로 하되, 대량 콘텐츠를 빠르게 편집해야 한다면 JSON/CSV 파이프라인도 가능. **초기부터 복잡한 범용 편집기를 만들 필요는 없다.**

### 3.4 콘텐츠 제작 가이드

- 대사: 한 카드당 **1~2줄**, 현재 상태 힌트도 짧게.
- 상태마다 판정에 영향을 주는 **최소 1개의 눈에 보이는 단서**를 제공한다.
- 시각 단서만으로도 어느 정도 유추할 수 있게 표정·의상·소품을 활용한다.
- 핵심 판정에 필요한 정보를 색상 하나에만 의존하지 않는다(색각 접근성).
- 캐릭터 고유 성향은 느슨한 사전 지식으로, **현재 상태는 이번 결정에 필요한 단서**로 작용해야 한다.
- 인물 반복 출현 시 직전과 동일한 상태·문구가 과도하게 반복되지 않도록 기본적인 중복 방지 로직을 고려한다.

---

## 4. 연출·아트·사운드

**분위기:** 귀엽고 약간 으스스한 할로윈 밤. 깊은 남색·보라색 배경에 호박색/사탕색 강조. Reigns의 **카드 드래그 인터랙션만 참고**하며, 캐릭터·그래픽·구성은 독창적으로 제작한다.

- 카드 중심의 큰 초상화. 표정이나 소품이 충분히 읽힐 것.
- 스와이프 방향에 따라 카드 기울기·선택 문구·아주 약한 컬러 강조.
- 성공 시 사탕이 HUD로 튀는 짧은 피드백; 실패 시 실망·화남 등의 개별 리액션.
- 카드 교체에 가벼운 효과음, 선택 결과에 서로 다른 사운드.
- 모바일 웹 브라우저의 오디오 재생 정책을 고려해 첫 터치/클릭 이후 소리 재생을 시작.
- 긴 대화창·스킵 불가능한 연출을 피한다. **한 카드가 한 번의 빠른 판단**이다.

## 5. 화면 상태 / 씬 흐름

| 화면 | 필요한 UI/동작 |
|---|---|
| 타이틀 | `START`, 간단한 조작 안내, 이전 최고 기록 |

### 6.3 스크립트 역할

- `GameManager`: `TITLE / PLAYING / RESULT / GAME_OVER` 상태 관리, 사탕 누적, 한 판 시작·종료, 인카운터 흐름.
- `EncounterGenerator`: 출현 캐릭터/상태/대사 선택, 동일 상태 과다 반복 제한.
- `CardController`: 포인터/터치 입력 수집, 드래그, 기울기, 방향별 미리보기, 임계값·확정·복귀, 한 번 선택 후 입력 잠금.
- `TimerController`: 전체 시간과 카드별 10초 시간의 업데이트/중단/만료. 중복 만료와 선택 확정 충돌 방지.
- `SaveManager`: 최고 기록 로컬 저장 및 로드(웹에서 저장 지속성 확인).

### 6.4 기술적 주의점

- **웹 Export는 GDScript 기반으로 진행.** Godot 4 C#을 웹 타깃의 기본 선택으로 사용하지 않는다.
- Compatibility 렌더러와 웹용 익스포트를 우선한다.
- 모바일 브라우저의 주소창 크기 변화, 터치 좌표, 화면 회전, 안전영역을 실기기에서 확인한다.
- 카드 드래그 임계값은 화면 크기와 카드 폭에 비례하도록 계산한다.
- 진행 타이머는 실제 경과시간(`delta`) 기준으로 처리하고, 중복 업데이트 및 백그라운드 탭 전환 처리를 명시적으로 정한다. 초기안: 탭 비활성화 시 일시정지 후 복귀 시 재개(악용 여부는 테스트).
- 브라우저 저장소가 차단되거나 삭제되면 최고 기록 보존을 보장할 수 없다.
- 배포 페이지에서는 캔버스가 모바일 세로 화면에 맞게 표시되며 불필요한 웹페이지 스크롤이 생기지 않도록 한다.

## 7. MVP 개발 우선순위

### P0. 손맛 확인 — 최우선

- [ ] 720×1280 기준 세로 `GameScreen` 씬 구성
- [ ] PC 마우스 + 모바일 터치로 카드 스와이프
- [ ] 좌우 미리보기 문구, 카드 기울기, 확정/취소, 다음 카드 전환
- [ ] 테스트 캐릭터 1종으로 동작 확인

### P1. 실제 플레이 루프

- [ ] 3분 전체 타이머(설정 가능) + 인물별 10초 타이머
- [ ] TRICK/TREAT 판정과 사탕 보상, 피드백
- [ ] 시간 초과 / 3분 종료 / 재시작
- [ ] 로컬 최고 기록
- [ ] 캐릭터 5종, 각 상태 2종 이상, 상태별 대사 2개 이상

### P2. 게임성 검증

- [ ] 같은 캐릭터 상태에 따라 유리한 선택이 달라지는지 확인
- [ ] 단서가 읽히고 선택 결과가 납득되는지 블라인드 테스트
- [ ] 10초가 압박감은 주되 지나치게 짧지는 않은지 확인
- [ ] 1회 플레이 이후 재도전 유도되는지 관찰
- [ ] 모바일 실기기 테스트(Android Chrome, iOS Safari 우선)

### P3. 합작 공개용 마감

- [ ] 최종 캐릭터 수·아트 확정 및 추가
- [ ] 짧은 효과음/결과 애니메이션/타이틀 화면
- [ ] 다양한 화면 비율 및 브라우저 검증
- [ ] Web Export 빌드, HTTPS 배포, 외부 링크 접근 확인

**범위 밖(초기):** 서버·랭킹·계정·온라인 저장·맵 이동·복잡한 이벤트 분기·대규모 절차 생성·다국어 지원. 재미 검증 후 별도로 판단.

## 8. 최소 완료 기준 (Acceptance Criteria)

1. **PC와 모바일 웹에서 실행**되고 세로 UI가 잘림 없이 표시된다.
2. 카드가 터치/마우스 드래그에 따라 **방향·기울기·선택 문구를 실시간 표시**한다.
3. 드래그가 임계치 미만이면 복귀하고, 초과하면 **정확히 한 번만 선택**된다.
4. 각 방문에 **10초 제한**이 적용되며 시간 초과 시 다음 카드로 진행한다.
5. 전체 한 판 종료까지 타이머가 정상 작동하고 **사탕 총점이 누적**된다.
6. **동일 캐릭터가 다른 상태와 대사**로 나올 수 있고, 이에 따라 유리한 선택도 달라질 수 있다.
7. 정답 판단에 필요한 단서가 화면에 표시되고, 결과에는 간결한 설명이 있다.
8. 종료 후 최종 점수, 최고 기록, 재도전을 제공한다.
9. 3분 플레이 동안 입력 누락·중복 판정·카드 정지·레이아웃 잘림이 발생하지 않는다.

## 9. 첫 플레이테스트 질문

- **판단 가능성:** 플레이어가 결과를 본 뒤 “아, 대사/표정 때문에 그랬구나”라고 이해하는가?
- **조작감:** 카드를 잡고 움직이는 감각이 명확하고, 오입력이 없는가?
- **시간 압박:** 10초 제한이 긴장감을 주면서도 텍스트를 읽을 시간을 남기는가?
- **반복성:** 같은 사람의 새로운 상태가 재미있고, 반복 출현이 지루하지 않은가?
- **경제성:** 높은 점수를 위해 더 빨리 고르고 재도전할 이유가 생기는가?
- **완주 경험:** 한 판을 끝낸 뒤 바로 한 번 더 하고 싶은가?

## 10. Local Work / Claude Code 첫 작업 지시문

> 이 문서를 기준으로 **Godot 4 + GDScript, Compatibility renderer** 기반 웹 미니게임 프로토타입을 구현한다. 첫 단계에서는 아트·콘텐츠 대량 생산보다 **720×1280 세로 UI와 Reigns식 카드 스와이프 손맛**을 우선한다. 카드 좌/우 선택은 TRICK/TREAT, 카드별 제한시간은 10초, 한 판 전체 시간은 기본 180초(쉽게 변경 가능)다. 주민의 고정 성향과 매 방문마다 다른 상태·대사·시각 단서에 따라 사탕 보상이 결정되게 하고, 판단 근거 없는 랜덤 정답은 금지한다. 마우스와 모바일 터치를 모두 지원하고, Web Export로 실제 브라우저 실행을 검증한다. 우선 P0→P1까지 구현한 다음 미구현 항목·테스트 결과·실행 방법을 보고한다. 게임 핵심 규칙이나 기획 방향을 변경할 필요가 생기면 임의로 바꾸지 말고 별도 제안으로 남긴다.

## 11. 미결정 사항(구현 전 기본값 사용 가능)

- 정식 게임 제목 및 타이틀 로고.
- 정확한 전체 한 판 시간(초기 180초), 보상 분포, 주민 총수.
- 시간 초과 시 페널티, 잘못된 선택의 사탕 손실 허용 여부.
- 카드 전환 효과·배경음·캐릭터 일러스트 스타일.
- 전역 시간 진행 중 브라우저 비활성화·일시정지 정책.
- 모바일 화면이 매우 좁을 때 선택 버튼 보조 UI를 표시할지 여부.

**기획 핵심은 변경하지 않는다:** *짧은 시간에 사람의 마음과 상태를 읽어 사탕을 최대한 얻는, 재도전 가능한 할로윈 카드게임.*
